## 2. Tauri 2.12.5 拖出 API 调查（关键）

直接阅读已安装 crate 源码（`%USERPROFILE%\.cargo\registry\src\index.crates.io-1949cf8c6b5b557f\`），结论如下。

### 2.1 唯一的 `start_dragging` 是「移动窗口」，不是文件拖出

```rust
// tauri-2.12.5/src/webview/webview_window.rs:2264
/// Starts dragging the window.
pub fn start_dragging(&self) -> crate::Result<()> {
    self.window.start_dragging()
}
```

```rust
// tauri-2.12.5/src/window/mod.rs:2364
/// Starts dragging the window.
pub fn start_dragging(&self) -> crate::Result<()> {
    self.window.dispatcher.start_dragging().map_err(Into::into)
}
```

```rust
// tauri-runtime-2.12.2/src/lib.rs:979
/// Starts dragging the window.
fn start_dragging(&self) -> Result<()>;
```

签名是 `fn start_dragging(&self) -> Result<()>`：**没有 paths 参数、没有拖拽图像参数**，文档注释明确是 “Starts dragging the window”。Windows 上 tao 把它实现为向窗口投递 `WM_NCLBUTTONDOWN` + `HTCAPTION`（`tao-0.37.2/src/platform_impl/windows/window.rs:493`），即标题栏式的窗口拖动；如果对面板调用，面板会跟着鼠标移动，而不是拖出文件。因此本任务**故意不调用它**。

### 2.2 没有出站文件拖拽实现

- 在 `tauri`、`tauri-runtime`、`tauri-runtime-wry` 的全部 `.rs` 中检索 `CF_HDROP` / `IDropSource` / `IDataObject` / `DoDragDrop`：**0 命中**。
- `DragDropEvent` 只描述**进入 webview 的**拖拽（`wry-0.57.1/src/lib.rs:2291`，`Enter/Over/Drop/Leave`）；Tauri 侧 `window/mod.rs` 只是重新导出。
- `WebviewBuilder::disable_drag_drop_handler`（`tauri-2.12.5/src/webview/mod.rs:630`）的注释说明 Windows 上 Tauri 替换了 WebView2 的拖放处理器，禁用后才能使用 HTML5 DnD；这同样是**入站/浏览器内**语义，不能把真实文件路径以 `CF_HDROP` 交给 Explorer。

### 2.3 对 brief Step 4 三个问题的回答

| 问题 | 结论 |
| --- | --- |
| 是否支持拖拽图像？ | **无此能力**。Tauri 2.12.5 的 `start_dragging()` 没有 image 参数；不存在文件拖出 API，因此也无从谈拖拽图像。 |
| 是否阻塞到拖拽结束？ | **不适用**。窗口移动版 `start_dragging()` 只向事件循环投递移动请求并立即返回；没有文件拖拽会话可等待。 |
| 是否支持 `CF_HDROP`？ | **否**。Tauri 不实现 `IDataObject`/`CF_HDROP`；需要自实现 OLE 拖源。 |

**结论：E4 的主路径（Tauri 原生拖出）在本版本不存在。** 按 brief，需在 Task 13 实现 OLE fallback（`IDropSource` + `IDataObject` + `CF_HDROP`，可选 `IDragSourceHelper` 拖拽图像），本任务不写 fallback 代码。另：把 HTML5 `draggable`/`DownloadURL` 当替代方案也已排除——浏览器生成的是副本/虚拟文件，拿不到原始真实路径，不满足「CF_HDROP 语义 + 不复制文件」的契约。

| 数据对象 | **首选 shell `IDataObject`**：`SHCreateItemFromParsingName(path)` → `IShellItem::BindToHandler(None, &BHID_DataObject, &IDataObject::IID)`（与 Explorer 自身拖拽同源，直接发布 `CF_HDROP`）。shell 失败时回退到**手写 `IDataObject`**：`GMEM_MOVEABLE` + `DROPFILES`（`pFiles=20`、`fWide=TRUE`）+ UTF-16 路径列表 + 双 `NUL`；仅支持 `CF_HDROP`（`QueryGetData`/`GetData`），`EnumFormatEtc` 返回 `E_NOTIMPL`（文件目标都直接查 `CF_HDROP`）。 |
| 拖源 | 手写 `IDropSource` vtable：`QueryContinueDrag`：Esc（`fEscapePressed` 或 `GetAsyncKeyState(VK_ESCAPE)`）→ `DRAGDROP_S_CANCEL`；左键仍按下（`MK_LBUTTON`）→ `S_OK`；已松开 → `DRAGDROP_S_DROP`。`GiveFeedback` → `DRAGDROP_S_USEDEFAULTCURSORS`（OLE 默认复制/移动/禁放光标）。 |
| `DoDragDrop` | `DoDragDrop(&data, &source, DROPEFFECT_COPY, &mut effect)`。**只允许 COPY**：目标只可能复制，源文件保留；move 语义属于 Task 13 的 prune 决策，不由拖源决定。 |
| 线程模型 | `start_drag` 校验路径 → `DragSession` 原子置位（防并发拖拽）→ **立即返回**；专用 STA 线程 `hangline-ole-drag` 执行 `OleInitialize` + 创建数据对象/拖源 + `DoDragDrop`（模态循环），结束后清除 flag，并通过 `emit_to("panel", "drag-ended", DragEnded)` 把 `{effect, dropped, error?}` 送给前端。IPC/主线程不再被 `DoDragDrop` 阻塞。 |
| 前端 | pointerdown 记录起点；pointermove 超过 4dp 后 `preventDefault()`（阻止 WebView2 的 HTML5 拖放）并 `invoke("start_drag", { path })`；`--dragging` 类保持按下视觉；监听 `drag-ended` 清除；`onDragStart` 也 `preventDefault`。 |
| 防穿透 | `DragSession` 覆盖整个 `DoDragDrop` 期间，`hittest` 在此期间不调用 `set_ignore_cursor_events`。 |
| 依赖 | **未新增 crate**。仅把已传递启用的 `windows` feature 显式化：`Win32_System_SystemServices`、`Win32_System_Com_StructuredStorage`、`Win32_UI_Input_KeyboardAndMouse`。 |

实现细节（为什么手写 vtable）：`windows::core::implement` 宏会展开成 `::windows_core::...` 绝对路径，要求把 `windows-core` 声明为直接依赖；为遵守「不新增依赖」，`IDataObject`/`IDropSource` 改为手写 vtable（`ComHeader`：vtable 指针 + 引用计数；静态 `IDropSource_Vtbl`/`IDataObject_Vtbl`；`QueryInterface` 支持 `IUnknown` + 对应接口）。该布局依赖 pinned `windows` 0.62 的 `*_Vtbl` 结构，升级 crate 时需重跑 §9.2 的 ignored 测试。

## 11. 真机拖拽修复（2026-11-10）：OLE 模态循环必须在面板 UI 线程

**真实用户反馈**：从晾图绳拖卡片到微信聊天框无反应（v1.3.0 已发布版本）。

**真机定位**（release 构建 + `drag-ended` 日志）：拖拽会话能启动、shell `IDataObject` 正常，但 `DoDragDrop` 的模态循环在 8 秒内只收到 **1 次 `QueryContinueDrag`、0 次 `GiveFeedback`**，被看门狗取消（`drag loop received no input`）。根因是拖拽跑在专用工作线程上：`DoDragDrop` 的鼠标捕获与模态消息循环没有拿到系统鼠标消息。

**修复**：`start_drag` 改为通过 `app.run_on_main_thread` 在**拥有面板窗口的 Tauri UI 线程**上排期拖拽（`DoDragDrop` 本身是模态的，它的消息循环会继续泵窗口消息，拖拽结束后事件循环立即恢复）。修复后同机实测：`QueryContinueDrag 44 次、GiveFeedback 46 次`，拖到资源管理器得到 `effect=copy` 且文件被复制（`after_drag` 保持卡片，源文件不删除）。

**验证边界**：拖到资源管理器已通过；微信 4.x 聊天框对 CF_HDROP 的接受情况单独探测（若目标返回 `DROPEFFECT_NONE`，属于目标方拒绝，需用复制+粘贴兜底）。
## 10. 复审修复（2026-10-29 12:50）：`DoDragDrop` 看门狗与丢失事件恢复

> Task 4 复审提出两个 Important findings：（1）前端只有 `drag-ended` 会清除 `dragging`，事件丢失会永久卡住卡片，报告里「下一次 pointerdown 会清除」不成立；（2）`DoDragDrop` 只在返回时清会话，输入丢失（锁定/UAC/安全桌面）会让模态循环挂住，`hittest` 永远跳过、后续拖拽全部 "already in progress"。本节记录修复，属于**防御性**改动：OLE/CF_HDROP ABI 与 COPY-only 语义不变，不新增依赖。

### 10.1 Rust（`src-tauri/src/dragout.rs`）

### 10.4 剩余限制

1. **看门狗只覆盖「一次输入都没有」的卡死**（复审要求的锁定/UAC/安全桌面场景）。已收到输入后「用户按住不动」与「输入再次丢失」无法区分，因此首次回调后看门狗主动退出；这类情况由前端 30 s 兜底与下一次 pointerdown 恢复 UI，Rust 侧会话可能保持到该线程返回。若产品需要，可在此机制上增加「输入静默超时」，但会与「按住不动」冲突，需要产品决策。

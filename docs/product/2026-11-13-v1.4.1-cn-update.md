> **文档性质**：v1.4.1 的**决策与验收口径**（实现随 v1.4.1 发布后由 lead 回写 §5）。不是用户手册；用户可见说明见 README 与 [发布说明](../release/notes-v1.4.1.md)。

> **关联文档**：[设计 spec §6.2–6.4 Amendment](../superpowers/specs/2026-10-28-hangline-windows-design.md)（网络契约）· [v1.4.0 绳子外观设计](2026-11-12-v1.4.0-rope-appearance.md)（前序版本）

## 0. 一句话

GitHub Releases 在部分中国大陆网络不可达，导致「检查更新」直接失败；v1.4.1 在**不改变「更新是唯一网络行为」承诺**的前提下，为更新清单与安装包增加**官方源优先 + 三个国内可访问镜像兜底**的通道，并用签名版本绑定防止镜像降级。

## 1. 问题与实测证据（2026-11-13 09:00，本机未挂 VPN）

| 请求 | 结果 |
|---|---|
| `https://github.com/devin2255/hangline/releases/latest/download/latest.json` | ❌ `http 000`（连接失败） |
| `https://ghfast.top/https://github.com/.../latest.json` | ✅ `200`，1368 B，JSON 正常 |
| `https://gh-proxy.com/https://github.com/.../latest.json` | ✅ `200`，1368 B |
| `https://ghproxy.net/https://github.com/.../latest.json` | ✅ `200`，1368 B |
| 三代理下载 `Hangline_1.4.0_x64-setup.exe` 前 1 MiB | ✅ `206`，`MZ` PE 头正确（三代理均通） |
| `https://api.github.com/repos/.../releases/latest` | ✅ `200`（本网络可通，但安装包下载域仍被墙，不能单独作为方案） |

结论：镜像能覆盖「清单 + 安装包」两条链路；官方源保留，镜像只做兜底。

## 2. 方案（A：公共镜像兜底；已被批准）

1. **发布流水线**：`build-release.mjs --sign` 在官方 `latest.json` 之外生成
   `latest-cn-ghfast.json`、`latest-cn-gh-proxy.json`、`latest-cn-ghproxy-net.json`；
   每份清单仅改写平台 `url`（加对应代理前缀），`version`/`notes`/`pub_date`/签名逐字节保留。
2. **客户端端点顺序**（`tauri.conf.json`）：
   官方 → ghfast → gh-proxy.com → ghproxy.net。Tauri updater 顺序尝试，第一个可解析清单即采用。
3. **超时分阶段**（`src-tauri/src/updater.rs`）：
   - 检查：每源 5 s（`CHECK_TIMEOUT`），被墙官方源快速失败；
   - 下载：不设总超时（插件默认），慢速网络可完成约 7 MB 安装包。
   注意：插件 `timeout` 是**整个请求**的总超时，因此只在 `check_updates` 的 updater 上设置，
   `install_update` 不继承（否则会掐断下载）。
4. **防降级**：开启 `requireSignedVersion`。清单仅 TLS 保护；签名可信注释含
   `version:1.4.x`，镜像若用「更高版本号 + 旧版真实安装包签名」会被拒绝。
5. **CI 校验**：`scripts/release/verify-cn-manifests.mjs` 校验三份清单的版本/notes/pub_date/
   平台键/签名一致、URL 前缀正确、签名含版本号；缺失或多余清单直接失败。
6. **配置漂移防线**：`scripts/check-update-endpoints.mjs`（`pnpm check` 内）校验
   `tauri.conf.json` 与 `scripts/release/update-mirrors.mjs` 完全一致、全 HTTPS、
   `requireSignedVersion=true`、`installMode=passive`。
7. **测试**：镜像清单生成器自测、端点配置一致性检查、Rust 单测（逗号分隔 debug endpoint 解析/
   非法 URL 拒绝/`CHECK_TIMEOUT`/配置端点顺序与安全标记）、本地更新 harness 新增
   「死端点 → 第二端点」回退场景；发布后在无 VPN 环境核验三镜像清单与安装包 SHA-256。

## 3. 安全分析

- **完整性与来源**：更新包始终由 minisign 校验；镜像只影响传输路径，不改变信任根。
- **降级攻击**：无 `requireSignedVersion` 时，恶意镜像可伪造更高版本号并指向旧版真实签名包。
  开启后签名版本与宣布版本必须一致，CI 也校验签名含版本号，因此镜像不扩大攻击面。
- **隐私**：镜像仅接收公开的清单/安装包请求；无用户数据、无遥测。官方源优先，仅在官方不可达时
  才走第三方代理。
- **运维风险**：公共代理可用性非 100%；三镜像 + 官方源互为兜底。若长期需要，可后续接入
  自建 Gitee/OSS 镜像（方案 B，需账号/域名），只需替换 `MIRRORS` 列表与重新发布。

## 4. 兼容与发布步骤

- v1.4.1 之前的构建没有镜像端点：国内用户需**手动安装一次 v1.4.1**（README/发布说明提供三个
  代理下载链接），此后自动/手动更新可用。
- 发布：版本 1.4.1 → `pnpm check`（含新检查）→ 本地 `build-release.mjs --ci` 体积门 + selftest →
  push + tag `v1.4.1` → CI 内 `--sign` 构建并 `verify-cn-manifests` → GitHub Release 上传
  setup/portable/latest.json/latest-cn-*.json/SHA256SUMS → 无 VPN 环境核验。

## 2. 内存基线（本次最重要的发现）

| 口径 | 值 |
|---|---|
| 主进程 RSS / Private | **39.4 MB / 12.7 MB** |
| WebView2 子进程（7 个，均属 `app.hangline.Hangline`）RSS | **531.6 MB** |
| 进程树总 RSS | **571.0 MB** |
| 进程树总 Private（较少受共享页重复计数影响） | **293.8 MB** |
| 句柄 / 线程（主进程） | 411 / 39 |

**结论**：spec 的「常驻内存 ≤ 150 MB」只在**只算主进程**时成立；按**整个应用进程树**计（这才是用户实际感受和任务管理器“应用”分组的真实口径），**超标约 2 倍（Private 293.8 MB）**。
**对迭代的含义**：任何“再加一个 WebView2 窗口”的方案（贴图 Pin、命令面板、录制 HUD）都应在立项前按 **+70～135 MB/窗口** 估算，而不是 +10 MB。这直接支持《借鉴评估》§9 争议 2 的结论：**贴图 Pin 暂不做**。

## 3. 其他发现（需回写文档/待验证）

1. **冷启动处在目标边缘**：首次启动 frontend ready 3035 ms，刚好触发 3 s 兜底；README 写的「冷启动到托盘 ≤2 s」在首次启动时不成立（二次启动 1.3 s 成立）。P0 曾测 debug 3415 ms。
2. **剪贴板格式比文档多两种**：实际写入 `PNG + CF_DIBV5 + CF_HDROP + CF_BITMAP + CF_DIB` 五种；README/spec 只写三种。多出来的两种是更好的兼容性兜底，应更新文档而不是修代码。
3. **OLE 拖拽看门狗**：应用日志 `dragout: OLE drag loop received no input within 8000 ms`。在合成输入下必然触发；**真鼠标是否也会触发需要真人验证**——如果会，这就是一个 P0 缺陷（拖拽是核心手势）。
4. **面板启动瞬间尺寸**：窗口创建 35 ms 时 rect 为 `0,0,2880,315`（150% 缩放尺寸），随后修正为 `0,0,1920,210`。若在 150% 屏上首次启动，可能有一帧尺寸跳变，建议排查（低优先级）。
5. **托盘图标存在但不可自动化**：日志确认已创建；UIA 无法定位托盘按钮（Win11 溢出区）。真人点击仍需回归。
